# Experiment Decision Rules — companion to `agent-tiers`

This file is a topic-reference companion to ref:skill/grimorio.agent-tiers — general knowledge, the same status as its
`./project.reference.md` and `./project.refusal-pattern.md` siblings, **not** a behavior file, because no single agent owns
these rules. It exists to close one specific gap: this repo ran a set of measured experiments on what actually
makes a grimorio instruction FIRE — ambient placement vs. a caller-brief restatement, narrow vs. broad triggers,
a tiering formula tested against the exact task it was built for, whether a Haiku clone should ever plan — and
those findings sat stranded in a branch's own working notes, re-derivable only by whoever happened to reopen
that branch. The CEO's own instruction, relayed by `grimorio.system-keeper` per grimorio-conduct rule 11 (not
independently quotable): turn the findings' CONSEQUENCE into a decision-rules skill reachable by BOTH an
authoring agent's own phase chain and the main loop — "both you and he," in his own words, not just "the finding
exists somewhere in a log."

**A citation-format note, stated rather than silently resolved.** Several of the rules below trace back to this
branch's own experiment log, a file that lives under `objectives/` — one of the four project-tree roots
ref:skill/grimorio.agent-writing#general-level-content-must-never-cite-project-level-or-code-level-state-hard-rule-ceo-ruling-2026-08-15
forbids a general-level file from citing at all, and which is deleted outright when the branch that owns it
closes. Citing it here would both break that hard rule and go dead the moment this branch merges — exactly the
stranding this file exists to fix. So where a rule's source is that log, the table below carries the finding's
measured SUBSTANCE inline (what was measured, the sample shape, the result) and names its old F-number only as
an informal label for a reader who still has the branch open, never as a resolvable pointer. Where a rule's
source is an already-general, non-ephemeral skill file, the table cites it normally.

## The seven rules

Each rule is stated `WHEN <situation> ⟶ <consequence>` in this corpus's own rule-form
(ref:skill/grimorio.prompt-writing-quality/project.format-guide.md#1-the-rule-form--opener-then--when-the-kind-takes-a-condition).
Each is stated CHECKABLE where a real check exists — a STATIC test (inspect a brief/plan/tiering call already
written) and a PROBE (spawn something and observe whether the discipline fires unasked) — the same row shape
(rule, source, a static check, a probe) a separate scratch grading instrument used for authoring TECHNIQUES,
adapted here to grade DECISIONS instead (what a spawning/tiering/probing agent chooses, never what ends up in a
written artifact); that instrument lived under `tmp/` and is not cited by path here, per the same ephemeral-
scratch reasoning the citation-format note above already states for the experiment log.

| # | Rule | Source | STATIC test | PROBE |
|---|---|---|---|---|
| 1 | **WHEN an instruction must actually COMPEL a spawned agent — not merely be quotable back if asked ⟶ place it inside the CALLER'S OWN SPAWN PROMPT as a numbered in-task step; NEVER trust ambient `CLAUDE.md`/skill-body placement alone to make it fire.** | This branch's own experiment log (F5/F7/F8 — see the citation-format note above): `CLAUDE.md` reaches every spawned agent and compels none — two probe agents quoted three prohibitions and the load-before-analysing clause verbatim, zero tool calls, then never acted on either. The fix that measurably works: an invocation prompt ordering the subject to re-read the file from disk and treat it as authoritative produced a FRESH read (proven by the subject quoting content that exists only on disk) and obedience to a plain rule found there, unprompted. A separate, independent probe on a different ambient clause (`CLAUDE.md`'s own opening `import:skill/grimorio.prompt-reading` bullet) failed to fire 5/5, both tiers, both directions, with fresh — never stale — wording, closing the "maybe it was just stale text" question. | Grep the actual spawn brief sent: does the obligation appear as its own numbered step in the TASK body, not only inside an imported skill's text or ambient project context? | Spawn an agent with the rule present ONLY in ambient `CLAUDE.md`/skill context, never restated in the brief; check whether the governed action fires unasked. |
| 2 | **WHEN a rule's own trigger condition is NARROW and BINARY — a yes/no pattern-match, never "any instruction" or "any analysis" ⟶ ambient placement (`CLAUDE.md`, a loaded skill body) can be expected to fire on its own.** **WHEN the trigger is BROAD or UNIVERSAL — true of nearly every task ⟶ it cannot; restate it in the spawn prompt instead (rule 1 above).** | Same log, different findings: a narrow, binary trigger ("is this text a PROMPT a model will read to steer what it does, or a RECORD nobody executes?") fired 4/4, both tiers, both directions, from ambient placement alone, with correctly-silent negative cells proving the design measured something real — against three separate probes of broad/universal triggers ("any instruction in this corpus"; "analyse a problem, write a check, or report a measurement") that produced no clean firing cell across two independent attempts. **The limit, also measured on the same log:** a separate broad-by-the-same-test clause ("survey before introducing code") fired 2/2 on Sonnet anyway — its compliant behaviour overlaps almost entirely with what a competent coder does regardless of the rule, so trigger-width predicts firing only for a PURELY obligation-driven rule (one that serves nothing but itself), never universally. | For a rule you are about to place ambient-only, state its trigger as one yes/no predicate; if answering it requires judging "does this apply to most tasks," it is broad and does not qualify for ambient-only placement. | Word the same obligation two ways — one narrow-binary, one broad/universal — spawn both ambient-only with nothing restating either in the brief; compare fire rates. |
| 3 | **WHEN deciding a Haiku-tier executor for MECHANICAL/CODE-volume work ⟶ gate the decision on whether the work is FULLY PRE-SPECIFIED with no judgment left; NEVER gate it on a bare registration-cost line-count formula alone.** | cite:skill/grimorio.agent-writing/system-keeper-phases/phase-4-authoring-coordination.md#steps — that phase's own step 6 states the registration-cost threshold (sum every skill in a same-type clone's Knowledge list via `audit-chain.mjs --shape`, plus its clone-executor phase files, against the mechanical-volume saving) as gating a SAME-TYPE `grimorio.prompt-writer` clone specifically; that same phase's own step 1 records the measurement that applying the formula to `verify-gen.sh` plus its selftest (~442 combined lines) against the mandatory grimorio-conduct+prompt-reading registration floor (~593 lines) would have REFUSED delegation for the exact task the CEO's original complaint was about. | Before tiering a mechanical-volume node to Haiku, confirm in writing that the FULL functional specification (every function's behavior, every edge case, the exact algorithm) is already decided — a line-count sum cited alone, with no such confirmation, fails this check. | Hand a tiering decision two mechanical-volume tasks of similar size — one fully pre-specified, one "roughly like this, use judgment" — check it correctly separates them regardless of which one scores higher on a line-count formula. |
| 4 | **WHEN a task decomposes into more than one INDEPENDENT target or domain ⟶ fan out ONE bounded node per target; NEVER bundle unrelated targets into a single child's brief to save a spawn.** | cite:skill/grimorio.fan-out/SKILL.md#the-caller-not-the-callee-owns-the-split-hard-rule-ceo-2026-08-10 — the caller, not the callee, owns the split: a child holds the splitting rule and does not retrieve it under a task cue, so the caller names the actual items in the brief, never relies on the child noticing, and never writes the split as a general exhortation to fan out. | For a multi-target brief, confirm each independent target has its own child (or an explicit, reasoned solo declaration per that skill's own independence test) — one child briefed on two-plus unrelated targets fails this check on its face. | Hand a planning pass a task with two genuinely independent targets; check it names both as separate items in the brief rather than folding them into one child's task description. |
| 5 | **WHEN the parent's own context is already heavy going into a WRITING/TO-BE phase ⟶ relaunch a FRESH child in clean context to do that writing; NEVER author from a context already spent on prior spawns and reports.** | cite:skill/grimorio.loop-and-graph/SKILL.md#3b-size-dependent-delegation--decide-the-graphs-shape-before-you-spawn-ceo-2026-08-21 — its own RELAUNCH-FRESH classification, one of three the planning step must name before the first child spawns: a parent that does everything itself is likely WEAK (thin, never reviewed by fresh eyes); a parent that does HALF itself is BIASED in the parts it kept; a fresh child fixes both failure modes, "push through on what's left" fixes neither. | Before a writing/TO-BE phase, check the plan artifact names one of DO-IT-YOURSELF / FAN-OUT-WITH-A-LIMIT / RELAUNCH-FRESH explicitly, with a reason — a plan silent on this classification fails this check. | Run an orchestrator through several prior spawns until its own context is heavy, then reach the writing phase; check whether it relaunches a fresh child or authors inline from the spent context. |
| 6 | **WHEN tiering a REASONING/diagnosis/planning task ⟶ NEVER Haiku.** **WHEN tiering a VERIFICATION/gate/review task ⟶ default Sonnet; NEVER Opus by default.** | cite:skill/grimorio.agent-tiers/SKILL.md#haiku-the-volume-tier--plan-on-sonnetopus-execute-on-haiku-review-on-sonnet ("NEVER give Haiku PLANNING. Judgement is exactly what it lacks; a planning task is the one shape of work that requires the latitude it does not have.") and cite:skill/grimorio.loop-and-graph/SKILL.md#3-the-graph--who-is-in-it-and-the-branch-rule ("NEVER run a verifier node — the probe, the code-reviewer, any gate that stands before a merge — on Opus by default. ALWAYS run it on Sonnet instead... a verifier that inherits Opus by default is exactly the cost leak agent-tiers' own critic-integrity floor exists to stop.") | Grep a tiering decision: a REASONING/planning archetype's assigned tier must never read `haiku`; a VERIFICATION/gate archetype's assigned tier must read `sonnet` unless a NAMED subtlety-escalation reason raises it, never a bare inherited `opus`. | Ask a spawning agent to tier a planning sub-task and a review sub-task in the same fan-out; check neither lands on the wrong side of this rule. |
| 7 | **WHEN probing whether a governance-file edit fires, in the SAME session that made the edit ⟶ order the probe subject to RE-READ the file from disk and QUOTE the changed clause back, BEFORE trusting a negative result.** | Same log as rules 1-2 (F5/F7, informal labels — see the citation-format note above): a probe subject's context is a SNAPSHOT taken at spawn time — two subjects quoted OLD, pre-fix wording of a clause already rewritten two commits earlier, which had invalidated a prior "the fix changed nothing" conclusion (that conclusion had measured the pre-fix file, never the fix). The corrective, separately measured: an invocation prompt ordering a disk re-read reliably produces a FRESH read, proven by the subject quoting content that exists only on disk — without that instruction a probe cannot distinguish "the edit does not compel" from "the edit was never seen." | Before reading any probe result about a just-edited governance file as evidence, confirm the probe brief instructed a disk re-read AND the transcript shows the subject quoting POST-edit content, never merely the probe's own claim of freshness. | Edit a governance file, then spawn a probe both WITH and WITHOUT the re-read instruction; confirm only the WITH arm reliably quotes the new wording. |

## How this file is reached

Two channels carry this file to the two readers the CEO named — an authoring agent's own phase chain, and the
main loop — never one alone:

- **The agent-side channel**: `.claude/skills/grimorio.agent-tiers/SKILL.md` names this file, so any agent that already
  loads `agent-tiers` before spawning or tiering reaches it too.
- **The main-loop-side channel**: `.claude/skills/grimorio.conduct/project.main-loop-only.md` names this file as a
  decision input the main loop consults before a tier/grimorio.fan-out/delegate-vs-self spawn call.

Neither channel is mechanically enforced — like most of this corpus, both stand on the reader loading the file
they were pointed at. -> ref:skill/grimorio.prompt-writing-quality#the-harness--grounding-an-obligation-into-a-checkable-determination-the-ceos-own-recurring-construct-formalized-here
for what would make this a stronger harness than prose, not invented here.
